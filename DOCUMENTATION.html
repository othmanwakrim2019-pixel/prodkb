1. High-Level Architecture 🏗️

ProdKB is a deeply containerized application running in Docker. The system segregates synchronous user traffic from heavy background jobs using Redis and BullMQ.

3. Deep Dive: Incident Automation & Lifecycle ⚙️

The platform prevents incidents from being trapped in "Pending" status by utilizing strict SLA (Service Level Agreement) background watchers and Auto-Assignment rules.

Incident State Machine

            stateDiagram-v2
                [*] --> PENDING : Created via API
                
                PENDING --> ACKNOWLEDGED : Engineer claims ticket
                PENDING --> ESCALATED : SLA Timer Expires (Worker)
                
                ACKNOWLEDGED --> RESOLVED : Solution applied \n + Log added
                ESCALATED --> ACKNOWLEDGED : Management claims ticket
                
                RESOLVED --> [*]

Background Job Queue (BullMQ) Workflow

Instead of slowing down the user experience when saving a ticket, ProdKB pushes the event to an asynchronous worker queue that handles external alerts (Slack, PagerDuty, Email) via BullMQ.

            sequenceDiagram
                actor User
                participant Express as Node.js API
                participant DB as PostgreSQL
                participant Redis as Redis (BullMQ)
                participant Worker as Background Worker
                participant Webhook as External System (Slack/API)

                User->>Express: POST /incidents (Create Ticket)
                Express->>DB: Save to Database
                DB-->>Express: Returns Incident ID
                
                Express->>Redis: Enqueue Job (e.g. "Incident.Created")
                Express-->>User: HTTP 201 Created (Instant UI Response)
                
                Note over Redis, Worker: Asynchronous Process Starts
                
                Redis->>Worker: Provide Job Payload
                Worker->>DB: Fetch associated Users/Teams mapping
                Worker->>Webhook: Perform HTTP POST (Trigger Alert)
                
                alt Success
                    Webhook-->>Worker: 200 OK
                    Worker->>Redis: Mark Job Completed
                else Retry (Max 3)
                    Webhook--xWorker: 500 Failure / Timeout
                    Worker->>Redis: Re-queue with Exponential Backoff
                end

4. Node.js Clustering & Metric Aggregation 📊

To fully utilize the hardware, Node.js forks multiple Express instances. The primary challenge is that Prometheus scraping would only get data from one worker at a time. The diagram below shows how the AggregatorRegistry solves this via IPC.

            sequenceDiagram
                participant Prom as Prometheus Scraper
                participant Master as Primary Node Process (Port 3002)
                participant W1 as Worker 1 (Port 3000)
                participant W2 as Worker 2 (Port 3000)

                Prom->>Master: GET /metrics (Every 15s)
                Master->>W1: IPC: "Give me your metrics"
                Master->>W2: IPC: "Give me your metrics"
                
                W1-->>Master: { http_reqs: 50, active_users: 12 }
                W2-->>Master: { http_reqs: 140, active_users: 8 }
                
                Note right of Master: Primary mathematical sum
Total HTTP = 190
Total Users = 20
                
                Master-->>Prom: Aggregated Metrics Format

5. Core Technology Details 💻

Component Technology Used Implementation Detail
Frontend Framework React 18 + Vite Using TypeScript and TailwindCSS. Extremely fast local HMR.
Form Validation React Hook Form + Zod Shared schemas between Backend (Express) and Frontend.
Database Pooling PgBouncer Operates in transaction mode to prevent Node.js cluster from exhausting PostgreSQL connections.
Authentication JWT + HTTP-Only Cookies Stateless access tokens (15m). Stateful Refresh tokens allowing forced disconnects.
File Storage MinIO (S3 API) Backend streams multipart/form-data to MinIO, never storing binaries in Postgres.
Observability Prometheus & Grafana & Loki Zero-blind-spot PLG stack. Tracks API latencies, DB queries, and centralizes backend logging.
